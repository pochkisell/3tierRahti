1. SAML and OAuth

SAML is an XML-based federation standard commonly used for enterprise single sign-on. An identity provider authenticates a user and sends a signed assertion to a service provider, which uses that assertion to establish the user's session. OAuth 2.0 is an authorization framework: it lets a client obtain limited access to a resource on a user's behalf through scoped, time-limited access tokens. OpenID Connect adds an identity layer to OAuth 2.0 for sign-in.

A company typically chooses SAML when integrating browser-based applications with an established enterprise identity provider and its single sign-on or federation setup. It chooses OAuth when an application needs delegated API access, such as allowing a service to read selected data from another provider without receiving the user's password. For modern sign-in, OpenID Connect is generally the relevant OAuth-based protocol; OAuth alone is not an authentication protocol.

2. Web Application Firewall (WAF)

A WAF inspects HTTP and HTTPS requests and applies web-specific rules before requests reach an application. Depending on its rules and configuration, it can detect or block common attack patterns such as SQL injection, cross-site scripting (XSS), malicious request payloads, and some automated abuse. It reduces exposure but does not replace secure application code, authentication, patching, or monitoring; rules can also produce false positives or miss new attacks.

For this application, the natural placement is at the public edge, before the Rahti Route forwards traffic to the Nginx frontend. That lets it inspect requests headed to both the frontend and the proxied Flask API while keeping the backend and database Services private. A WAF would not normally sit between the backend and MySQL, because that connection is database traffic rather than HTTP.

4. YAML and Kubernetes configuration

YAML is a human-readable data-serialization format often used for configuration. Kubernetes and Rahti manifests use it to describe resources such as Deployments, Services, Routes, ConfigMaps, and Secrets. Its indentation makes nested structures easy to scan, and comments can explain configuration choices. These traits make YAML convenient for infrastructure files that people regularly review and edit.

JSON represents the same basic structures with braces, brackets, and quoted keys. It is widely supported by tools and APIs, but is often more verbose to edit by hand and does not support comments in standard JSON. YAML is not a different Kubernetes data model: manifests are parsed into structured data, and many Kubernetes tools also accept JSON. YAML's indentation is significant, so incorrect spacing can change or invalidate a manifest.

5. Public APIs and a realistic integration

Examples of public APIs include Open-Meteo for weather forecasts, the REST Countries API for country information, and the Open Library API for book metadata. Before choosing one, a developer should check its licence, rate limits, availability, data freshness, and authentication requirements.

A practical addition to this Flask application would be a weather summary endpoint backed by Open-Meteo. The backend could request a forecast for a configured location and return a small, stable response to the frontend. It should set connection and response timeouts, validate the upstream response, and handle provider failures without taking down the visitor counter. If the provider requires an API key, it belongs in a Secret rather than in source code or a ConfigMap.

The Route still exposes only the frontend. Flask communicates with Redis and MySQL through their internal Services. MySQL remains the durable source of truth; Redis stores only a temporary copy of the /api response.

Connection to the Week 5 Redis extension

The application adds Redis as a separate Deployment and Service and uses it to cache a Flask response. Caching can reduce repeated database work, but the application must define when cached data expires or is invalidated. In this visitor-counter example, a successful visit update must not leave a stale cached count visible. If Redis is unavailable, the backend should have a deliberate fallback policy, such as reading from MySQL, and Redis should remain reachable only by the application components that need it.
