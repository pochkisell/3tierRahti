MySQL Visitor Counter on Rahti

Open application · GitHub repository

1. Application overview

This application demonstrates end-to-end communication across three tiers. The frontend displays the current MySQL server time and a persistent visitor counter. Selecting Record a visit sends a POST request to the backend, which increments and stores the counter in MySQL.

2. Architecture and communication

Internet → Route → frontend Service → Nginx Pod
                                  │ /api
                                  ▼
                           backend Service → Flask Pod(s) → db Service → MySQL Pod → PVC

Only the frontend is exposed through a public Rahti Route. The frontend calls backend:8000; the backend calls db:3306. These names are internal Kubernetes Services, so Pod IP addresses are never hard-coded.

3. Configuration and secrets

ConfigMap app-config provides non-sensitive settings: DB_HOST, DB_NAME and DB_USER. Secret mysql-secret provides DB_PASSWORD and MYSQL_ROOT_PASSWORD. Password values are not committed to Git.

A Secret is intended for sensitive data and access is controlled separately. A ConfigMap is ordinary non-secret configuration.

4. Database persistence experiment

Method: record a visitor count, delete the MySQL Pod, wait for its replacement, then reload the application. 

oc delete pod -l app=db
oc get pods -w

Evidence to record: count before restart: [N]; count after restart: [N]; new MySQL Pod: [name].

The data survives because MySQL mounts the PersistentVolumeClaim at /var/lib/mysql. In Docker Compose the volume is local to the Docker host; in Rahti the PVC is a Kubernetes storage resource that survives Pod replacement and is reattached to the replacement Pod.

5. Pod recovery experiment

oc delete pod -l app=backend
oc get pods -l app=backend -w

Evidence to record: deleted Pod [old name]; replacement Pod [new name].

The backend Deployment owns a ReplicaSet. The ReplicaSet continuously maintains the desired number of replicas, so deleting a Pod causes Kubernetes to create a replacement automatically.

6. Scaling experiment

oc scale deployment/backend --replicas=3
oc get pods -l app=backend
oc get endpoints backend
oc scale deployment/backend --replicas=1

Evidence to record: backend Pods while scaled: [three Pod names]; final replica count: 1.

The frontend keeps using the stable DNS name backend. The backend Service selects all ready backend Pods and routes requests to their endpoints, without exposing individual Pod IP addresses to the frontend.

  • Configured Nginx to use writable /tmp directories and port 8080 under Rahti's non-root security policy.

9. Rahti compared with Docker Compose + cPouta

Docker Compose starts related containers and local volumes on one Docker host; networking is configured by the Compose file. In Rahti, desired state is declared as Kubernetes resources: Deployments recreate and update Pods, Services provide stable internal networking and load balancing, a Route exposes only the frontend, and a PVC manages persistent storage independently of a particular Pod. This makes the application managed and recoverable by the platform rather than by manual container restarts.
