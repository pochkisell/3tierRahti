Part A — Questions

1. CI, CD and Continuous Deployment

Continuous Integration (CI) is the practice of merging code changes frequently and validating them automatically. In a typical project, CI includes building the backend image, running tests, and checking whether the application still compiles correctly. Continuous Delivery (CD) means that the application is kept in a releasable state, but deployment to production may still require a final human decision. Continuous Deployment goes further: if a change passes all checks, it is automatically deployed to the target environment.

In this project, CI refers to building the Flask backend and pushing a new container image, while delivery and deployment refer to the release of that image into the Rahti cluster. The crucial difference is that delivery retains a manual gate, whereas deployment removes it and accelerates the flow from code to running application.

2. GitHub Actions workflow structure

A GitHub Actions workflow is described in a YAML file under .github/workflows/. It is triggered by events such as push or pull_request, and it contains one or more jobs. Each job runs in a runner and consists of several steps, for example checkout, dependency installation, container build, test execution, and deployment commands. A minimal workflow for this application should build the backend image, push it to a registry, log in to Rahti, and update the backend deployment with the new image tag. 

name: Build and deploy backend
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
      - uses: docker/build-push-action@v6
      - name: Deploy to Rahti
        run: |
          oc login "$RAHTI_SERVER" --token="$RAHTI_TOKEN"
          oc project "$RAHTI_PROJECT"
          oc set image deployment/backend backend="docker.io/${DOCKERHUB_USERNAME}/backend:${GITHUB_SHA}"

5. Liveness versus readiness probes

A liveness probe tells Kubernetes whether a container is still alive and should be restarted. If the probe fails repeatedly, Kubernetes restarts the container in order to recover from a stuck or unhealthy process. A readiness probe answers a different question: is the container ready to receive traffic? If readiness fails, the pod is removed from the Service endpoints, but the container itself is not necessarily restarted.

In this backend, the liveness probe checks /api/health, while the readiness probe checks /api/ready. The readiness endpoint performs a database connectivity check. If MySQL is unavailable, the pod is marked unready and traffic is diverted away from it until the dependency is restored.

7. Why secrets must not be hard-coded

Registry tokens, cluster login tokens, and similar credentials must never be written directly into a CI/CD workflow file because the file is part of the Git repository. Even if a repository is private, credentials may be exposed through repository access, forks, or a later compromise. Once a token is leaked, an attacker may publish a malicious image or gain access to the deployment environment.

GitHub Actions addresses this issue by using repository or organization secrets. Values such as DOCKERHUB_USERNAME, DOCKERHUB_TOKEN, RAHTI_SERVER, RAHTI_TOKEN, and RAHTI_PROJECT are stored in GitHub Secrets and then referenced in the workflow as ${{ secrets.NAME }}. This keeps credentials out of source control while still enabling secure runtime authentication.

Part B — Hands-On: Automate & Observe Your App

Workflow 
name: Build and deploy backend
on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: docker/login-action@v3
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}

      - uses: docker/build-push-action@v6
        with:
          context: ./backend
          push: true
          tags: docker.io/${{ secrets.DOCKERHUB_USERNAME }}/backend:${{ github.sha }}

      - name: Install OpenShift CLI
        run: |
          curl -fsSL https://mirror.openshift.com/pub/openshift-v4/x86_64/clients/ocp/stable/openshift-client-linux.tar.gz -o oc.tar.gz
          tar -xzf oc.tar.gz
          sudo mv oc /usr/local/bin/oc
          oc version --client

      - name: Deploy to Rahti
        env:
          RAHTI_SERVER: ${{ secrets.RAHTI_SERVER }}
          RAHTI_TOKEN: ${{ secrets.RAHTI_TOKEN }}
          RAHTI_PROJECT: ${{ secrets.RAHTI_PROJECT }}
          DOCKERHUB_USERNAME: ${{ secrets.DOCKERHUB_USERNAME }}
        run: |
          oc login "$RAHTI_SERVER" --token="$RAHTI_TOKEN"
          oc project "$RAHTI_PROJECT"
          oc set image deployment/backend backend="docker.io/${DOCKERHUB_USERNAME}/backend:${GITHUB_SHA}"
Evidence

Structured logging

import json
import time
from flask import Flask, g, jsonify, request

@app.before_request
def start_request_timer():
    g.request_started_at = time.perf_counter()

@app.after_request
def log_request(response):
    duration_ms = round((time.perf_counter() - g.request_started_at) * 1000, 2)
    app.logger.info(json.dumps({
        'event': 'http_request',
        'method': request.method,
        'path': request.path,
        'status': response.status_code,
        'duration_ms': duration_ms,
    }))
    return response

Problems encountered and solutions

Problem Cause Solution
GitHub Actions failed during `oc` installation The installer was trying to download a broken URL for OpenShift CLI version 4.16. Switched to the stable OpenShift mirror and installed the CLI manually with curl and tar.
Readiness needed to reflect real application health A simple /api/health check is not enough when MySQL is down. Added /api/ready with a real database query so the Service only routes traffic to healthy pods.
Secrets must not be stored in YAML Workflow files are stored in Git and should not embed credentials. Moved registry and cluster values to GitHub repository secrets and referenced them as ${{ secrets.NAME }}.
